# Limitations and what was NOT verified

Stated plainly so nothing is claimed that was not tested.

## External limitations of the build environment
1. **Docker.** Verified twice, in two environments. (a) *Build environment:* Docker Hub is blocked there, so `python:3.13-slim`, `redis:7-alpine`, Jaeger, Prometheus, Grafana and cAdvisor could not be pulled; the application image was built from this repository's `Dockerfile` with only the `FROM` line changed to a local Python 3.13 image, and `docker compose up --scale worker=3` ran the application services (api, 3 workers, ingest, chroma, redis, llm-stub) with the real `docker-compose.yml`. (b) *Demonstration laptop (Windows 11, Docker Desktop 4.97, WSL 2, 12 vCPU / 7.4 GB, 2026-10-29):* `docker compose up -d --build --scale worker=3` from a clean extract brought up **all 11 services with their official images** - redis, chroma, llm-stub, ingest (exit 0), api, worker x3, jaeger, prometheus, cadvisor, grafana - all `running`/`healthy`. Demonstration items 2, 4, 5, 6, 7 and 10 were then run there over HTTP.
2. **No real language model was used.** All agent runs here used either the *offline deterministic policy* (which is **not** an LLM: a rule-based planner that calls the same tools; it is the default in `.env.example` so that a clean start always serves correct answers) or the fixed-response *stub*. The LLM client (timeouts, retries, backoff, breaker, fallback, token/cost accounting), the tool loop, the verifier and the full HTTP path are real and tested; the model's actual reasoning quality, and therefore the real accuracy of the system, is **unmeasured**. The prompt comparison (L2) is unrun for the same reason.
3. **Semantic embeddings were not run** (sentence-transformers needs a model download). Everything was measured with the lexical `hashing` backend.
4. **OpenTelemetry export to Jaeger** is tested in the build environment with an in-memory exporter (spans, run id attributes, traceparent propagation across the queue). The OTLP network path to a real Jaeger was **confirmed on the demonstration laptop**: the Jaeger UI lists both services and shows each run as one trace spanning `api` (5 spans) and `worker` (17-25 spans), i.e. the correlation survives the Redis queue hop between two separate containers (D5).
5. **Grafana dashboard rendering.** The dashboard queries are syntax-checked as PromQL (23 panels) and every metric they read is asserted present by `test_metrics_are_exposed`, but rendering a panel needs a browser against a live Prometheus, which the build environment cannot do. The panels are therefore proven by screenshots taken on the demonstration laptop - see `docs/evidence/README.md` for the three captures and what each one closes (A6, L6, D5). One real defect was found this way: cAdvisor emits no per-container series under Docker Desktop / WSL 2, so the three resource panels were permanently empty; they now read the services' own process metrics instead (INC-N). cAdvisor is still scraped but nothing on the dashboard depends on it, so per-*container* (as opposed to per-*process*) utilisation is not shown on a Docker Desktop host. cAdvisor metric names (`container_cpu_usage_seconds_total`, `container_start_time_seconds`) and the `name=~"export-classifier-.+"` filter are standard but unverified on your host.

## Design limitations
* The corpus is **three PDFs for two chapters**; anything else escalates to specialist review by design. Tariff headings outside Chapters 73/96 are not indexed, so the system cannot know about them (it recognises "not named in my corpus", not "belongs to heading 6109").
* Only **heading level (4-digit)** classification is proposed; the tariff-item (8-digit) lines are shown with their export policy, not selected.
* Export policy is quoted verbatim from the supplied schedule with the caveat "confirm it is current before filing". Policy conditions that live in a footnote not parsed into the chunk may be missed (one condition chunk was extracted: `CH96-POLICYCOND-1`).
* The offline policy contains small common-language lexicons (materials, filler words); **no tariff knowledge** - which heading names an article is always decided from corpus text.
* Evaluation set was authored by the same team as the matcher (see `docs/EVALUATION.md`): treat 31/31 as a regression result. Metrics are deterministic proxies, not TruLens.
* The vacuum-flask result lists "alternatives" drawn from Chapter 73 headings (e.g. 7323/7307/7304) that were retrieved by the material search; the explicit exclusion shown is Section XV Note 1 against 7323. The reference answer in the Evaluation 1 plan expected 7323 as the excluded alternative - it is present.
* The local `redis` has persistence `appendonly yes` in compose; runs older than `RUN_TTL_S` (7 days) are deleted.
* One shared rate-limit key per `X-Client-Id`; a malicious caller can rotate the header. In production the id should come from authenticated identity (no authentication is implemented; out of scope for the brief).
* Only the vacuum-flask script exists in the stub; it ignores the product description. For any other product the verifier rejects that answer (`article_grounded_in_request`, `heading_matches_request`) and the run escalates with `verification_failed` - correct, safe behaviour, but it means the stub is only for load testing and the breaker demonstration. Before 2026-10-28 the verifier did **not** catch this (INC-J).
* A free tier with a low tokens-per-minute cap may not sustain even one run per minute: a run sends about 15 000 prompt tokens over its 5 calls (`docs/LOADTEST_RESULTS.md`, cost section).
* A broker decides: no output is a customs determination and none is ever phrased as one (output filter + `determination_authority`).
